# Журнал ошибок

## 2026-08-31 — Ideogram Background Remover обработал только 1 из 3 файлов

- Статус: Fix prepared — preflight `160aef0` блокирует весь batch до первого
  платного вызова; terminal-reason fix `77fad17` сохраняет реальную причину.
  В `develop/3.1` ещё не интегрировано, Windows-сборка не выполнялась.
- Симптом: в Fal.ai Ideogram Background Remover переданы три PNG 4096×4096, но
  фон удалён только у одного; итог запуска: 1 success и 2 errors.
- Evidence: файл №2 размером 5 988 703 байта был отправлен как единственная
  Fal.ai задача и успешно вернулся с usable alpha. Файлы №1 размером
  11 956 256 байт и №3 размером 9 547 385 байт получили локальную ошибку
  «Локальное изображение слишком велико для Fal.ai» до отправки провайдеру.
- Корневая причина: общий импорт Processing принимает файл до 100 МБ, но
  `fal_image_data_uri()` ограничивает встроенный local-image payload восемью
  мегабайтами. Provider-specific preflight этого ограничения не выполняет,
  поэтому платный batch начинается и лишь затем частично отклоняется.
- Стоимость: создана ровно одна платная задача удаления фона — для файла №2;
  два превышающих лимит файла провайдеру не отправлялись.
- Дополнительный дефект диагностики: общий `run_failed` получил
  `reason=missing_completion`, хотя обе реальные ошибки уже известны как
  `processing_error` с причиной превышения размера.
- Требуемое поведение: до подтверждения и первого платного запроса проверить
  весь batch по ограничениям выбранного провайдера, показать конкретные файлы и
  не начинать частичный запуск. Для больших файлов отдельно согласовать либо
  безопасную загрузку в Fal storage без потери качества, либо явное создание
  оптимизированной временной копии; исходники не изменять.

## 2026-08-31 — запуск только «Экспорт 300 DPI» отклоняет все файлы

- Статус: Fix prepared — `4484f89` признаёт 300 DPI самостоятельным локальным
  этапом. В `develop/3.1` ещё не интегрировано, Windows-сборка не выполнялась.
- Симптом: владелец выбрал только 300 DPI для 81 файла; интерфейс разрешил
  запуск, но через 1,36 секунды показал 81 ошибку «Не хватает обязательной
  настройки запуска». В `rough/` и `output/` новые файлы не появились.
- Evidence: журнал запуска содержит корректные активные стадии
  `export_300_dpi, export`, после чего каждый из 81 файлов получил одинаковый
  `reason=configuration`: «Включите хотя бы один этап…».
- Корневая причина: `_mode2_process_files()` умеет сохранить PNG с 300 DPI, но
  его начальная проверка допустимых операций не включает
  `self.export_300_dpi`. Поэтому валидный DPI-only запуск отклоняется до чтения
  и сохранения первого файла.
- Влияние: обработка не начиналась, поэтому отсутствие промежуточных файлов в
  `rough/` ожидаемо. Новых Fal.ai tasks в момент этого запуска нет, платных
  запросов и списаний не было.
- Требуемое поведение: считать `export_300_dpi` самостоятельной локальной
  операцией, проверять это до перехода на экран выполнения и создавать по
  одному новому PNG на вход с DPI 300 без изменения пиксельных размеров.

## 2026-08-31 — интерфейс зависает при добавлении 81 большого PNG

- Статус: Fix prepared — `dee9e6a` убирает полное декодирование с UI-потока,
  кэширует сведения, лениво загружает миниатюры и проверяет пиксели в worker до
  платного Fal-вызова. В `develop/3.1` ещё не интегрировано.
- Симптом: при перетаскивании в режим Processing 81 большого уже
  апскейленного изображения окно надолго перестаёт отвечать.
- Корневая причина: `dropEvent()` синхронно вызывает `add_files()` в GUI-потоке.
  Для каждого файла `inspect_local_image()` выполняет `Image.load()`, то есть
  полностью декодирует PNG. Затем `refresh_from_state()` повторно полностью
  декодирует все выбранные файлы и сразу читает миниатюру каждого файла через
  `QImageReader`. При одном drop из 81 файла интерфейс не обрабатывает события,
  а объём декодированных пикселей создаёт дополнительное давление на память.
- Временный обход для старой сборки: добавлять по 5–10 файлов и ждать обновления
  списка. После интеграции `dee9e6a` ручное дробление пакета не должно быть
  обязательным; остаётся Windows-проверка на исходных 81 больших PNG.
- Требуемое поведение: принимать пути сразу, проверять и индексировать файлы в
  фоновой очереди с прогрессом и отменой; хранить результат проверки, а
  миниатюры создавать лениво только для видимой части списка. Ошибки отдельных
  файлов должны отображаться пофайлово, не блокируя остальные.

## 2026-08-31 — Recraft сохраняет в rough вход и результат как один этап

- Статус: Fix prepared — `b1ce31d` публикует только фактический результат и
  использует уже скачанный Fal PNG для финала. В `develop/3.1` не интегрировано.
- Симптом: для batch из 17 файлов в `rough/` появились 34 файла с одинаковой
  меткой `upscaled-before`; визуально это выглядит как двойная обработка.
- Корневая причина: подготовленный до запроса файл
  `file_upscaled_before_recraft_input_*` и скачанный результат
  `file_upscaled_before_fal_*` оба содержат подстроку `upscaled`. Широкое
  правило `_persist_rough_outputs()` ошибочно публикует оба как одну стадию.
- Дополнительный дефект: диагностика содержит 34 события скачивания для 17
  Fal.ai tasks. Результат сначала скачивается в `.run`, затем тот же URL ещё раз
  скачивается во временный финальный файл. Это не создаёт вторую платную задачу,
  но расходует время, сеть и усложняет диагностику.
- Ожидаемое поведение: один meaningful post-upscale файл в `rough/` на каждый
  вход; финальная публикация должна использовать уже проверенный локальный
  результат без повторного скачивания.

- Расхождение: приложение записало `item_finished/succeeded` и `run_finished`

## 2026-08-14 — installer собирал клиент со старым протоколом лицензий

- Симптом: release workflow мог собрать Clipart Generator 3.0, но desktop-клиент
  обращался к legacy-маршрутам `/activate`, `/validate` и `/status`, тогда как
  развёрнутый License Service принимает `/api/v1/licenses/activate` и
  `/api/v1/licenses/validate` с Ed25519-доказательством устройства.
- Корневая причина: сервер и desktop-разработка завершались раздельно, а в
  release gate не было межпроектного contract-теста. Наличие старых локальных
  тестов клиента ошибочно выглядело как готовая интеграция.
- Исправление: desktop переведён на фиксированный HTTPS endpoint, стабильный
  `product_id`, свежие nonce/proof и проверку подписанного ответа по закреплённому
  публичному ключу. Офлайн-разрешение удалено; все три V3 worker boundary
  требуют успешной онлайн-проверки.
- Регрессия: `tests/test_license_client_security.py`,
  `tests/test_v3_license_flow_gate.py` и
  `tests/test_license_service_contract.py` проверяют подпись, границы запуска и
  полный цикл «выпуск → активация → проверка → отзыв → отказ».

## 2026-08-14 — workflow мог завершиться без доступного инсталлятора

- Симптом: шаг загрузки Windows-артефакта имел `continue-on-error: true`, поэтому

- Регрессия: release workflow использует `if-no-files-found: error`; после
  сборки скачанный SHA-256 дополнительно сверяется локально.

## 2026-08-15 — приложение открывалось без startup-проверки лицензии

- Симптом: установленное приложение открывало выбор режима без запроса ключа;
  ввод лицензии был доступен только через малозаметную кнопку внутри режима.
- Корневая причина: онлайн-авторизация была установлена на границах worker и
  retry, но фактическая release-точка входа вызывала
  `create_v3_application_window()` без обязательного startup-барьера.
- Исправление: release-точка входа создаёт основное окно только после свежей
  онлайн-проверки сохранённой лицензии либо успешного ввода и повторной проверки
  нового ключа. Отмена, отсутствие gate, офлайн или отказ сервера закрывают
  запуск до показа основного интерфейса.
- Регрессия: `tests/test_release_entrypoint.py` проверяет отказ до открытия,
  онлайн-проверку сохранённой лицензии, повторную проверку после активации и
  fail-closed поведение при отсутствующем gate. Release workflow также запускает
  новый `--release-entrypoint-smoke` внутри собранного `.exe`; он проверяет
  наличие маскированного поля ключа и отказ startup при отклонённой лицензии.

## 2026-08-15 — установленное приложение предлагало Program Files для результатов

- Симптом: у нового проекта не было сохранённой рабочей папки, поэтому системный
  диалог мог открываться в каталоге установленного `.exe`, включая `Program Files`.

  пользовательский вариант.
- Регрессия: `tests/test_v3_mode_selection.py` проверяет новый путь независимо от
  каталога процесса и восстановление обоих выбранных путей после перезапуска.
