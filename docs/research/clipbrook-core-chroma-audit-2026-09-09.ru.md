## Повторная проверка: фактический запуск исходного движка, 2026-09-09

Ниже сохранён первоначальный аудит полностью. Этот раздел дополняет его
измерением результата самого upstream, а не выводами только по чтению кода.

Повторно прочитаны `classify.ts`, `band.ts`, `chromaKey.ts`, `types.ts`,
`finish.ts`, `despill.ts`. Копия upstream имеет тот же SHA
`c1473ae2c7d60f3beb7a56b46045c91bcf896945`, `git status --short` пуст.
Запущен оригинальный `chromaKey` через Node 24.15.0 с встроенным
`--experimental-transform-types`; локальный адаптер разрешает расширение `.ts`
у относительных импортов. npm-зависимости не устанавливались. В приложение
не добавлены ни upstream, ни Node, ни новые зависимости.

### Что проверено

Входы шести существующих fixtures прочитаны через `load_golden_fixture`,
который проверяет hash manifest. Исходные RGBA-байты переданы оригинальному
движку без масштабирования и без PNG-кодека. Сначала использованы все default
параметры. Результаты сравнены с Vibix `opaque_clipart` v2 одной и той же
float-метрикой `reference_quality`; это сравнение локальных движков, не сайта
Clipbrook и не его возможных дополнительных настроек.

Ошибка цвета на чёрной подложке, p95 только в области истинной частичной
coverage; шкала 0…1, меньше лучше:

| Fixture | Vibix v2 | Clipbrook defaults |
| --- | ---: | ---: |
| soft-edge-red | 0.281892 | 0.245675 |
| thin-lines-green | 0.229846 | 0.177532 |
| openings-blue | 0.269158 | 0.194802 |
| partial-alpha-red | 0.291826 | 0.499316 |
| color-spill-green | 0.174833 | 0.350173 |

На clean-edge-blue частичной coverage нет; пустая область не считается нулевой
ошибкой. Оба движка сохранили его геометрию. Таблица не является общим рейтингом
качества. Размер эталонов 256×256; фиксированные радиусы и размер островков
upstream особенно чувствительны к масштабу. Частично прозрачный fixture не
является целевым материалом opaque clipart, но выявляет пределы метода.

### Какой принцип действительно помогает

`classify.ts` перепроверяет подозрительную непрозрачную кромку до решения смеси.
Это отличается от поздней RGB-коррекции Vibix. Для разделения влияний отдельно
запущен upstream с `rimSlopeGain=0, rimSlopeBias=1.15`: отключается адаптация
порога к глубинному цвету, но не вся возможность demotion ранее promoted core.
На soft-edge-red число demoted pixels изменилось 1795→0, а средняя ошибка
alpha в partial ROI ухудшилась 0.085703→0.120244. На openings-blue:
238→0 и 0.040886→0.057164. Это причинная проверка пользы адаптивной перепроверки
кромки в этих сценах. Однако p95 ошибки цвета не изменился, а на color-spill
этот же механизм ухудшает alpha. Следовательно, одной demotion недостаточно:
нужны проверки надёжности опорного цвета и отказ от решения при конфликте.

### Проверка именно узкого края и мелкого объекта

Дополнительно сформированы три непрозрачных квадрата 256×256 с единственным
верхним рядом coverage128/255. Основной квадрат занимает `[32:224,32:224]`.
На синем фоне, foreground `(120,80,180)`, в точке `(128,32)`:

- эталон: `(120,80,180,128)`;
- Vibix: `(120,80,179,128)`;
- upstream defaults: `(60,40,217,0)`.

На красном фоне с foreground `(75,172,226)` alpha Vibix124, upstream116,
эталон128. На зелёном с foreground `(205,132,190)` alpha Vibix125,
upstream117. Поэтому нельзя считать сам факт использования upstream гарантией
лучшего узкого края. Эти три квадратных случая также не заменяют реальные
клипарты с волосами и ветками.

Отдельная причинная проверка `minIsland`: к большому непрозрачному квадрату
добавлен изолированный квадрат 16×16 того же цвета `(200,120,90)` на синем фоне.
Default upstream удалил его полностью, alpha в `(222,222)` стала0.
При единственной смене `minIsland=0` alpha осталась255. Это конкретный риск
для отдельного цветка или листика, не только потеря слабого сглаживания.
Метрику support>=1/255 нельзя трактовать как долю потерянных реальных объектов:
она учитывает также очень слабую coverage и ringing синтетического ресайза.

### Решение и следующий шаг

Не заменять рабочий путь upstream defaults и не переносить фиксированную
очистку мелких островков. Следующий кандидат для самостоятельной реализации:
проверка подозрительной кромки **до** окончательного назначения alpha, вместе
с локальной проверкой качества опорного цвета. Проверять отдельно на узком
AA, градиентном foreground, key-подобном foreground, волосах/ветках и островках.
Не объявлять текущий алгоритм качественным: основная проблема маски остаётся.
Нужна исходная PNG/результат пользовательского примера; screenshot не позволяет
отделить ошибку keyer от исходного RGB, апскейла и последующей обработки.

Локальный адаптер и результаты (исследовательские, не runtime):
`.scratch/run-upstream-reference.mjs`, `upstream-inputs.json`,
`upstream-results.json`, `upstream-comparison.json`,
`upstream-no-adaptive-rim.json`, `upstream-no-finish-trimming.json`,
`upstream-crisp-inputs.json`, `upstream-crisp-results.json`,
`upstream-island-input.json`, `upstream-island-default.json`,
`upstream-island-preserve.json` в той же `.scratch/`.

Независимая проверка Terra воспроизвела все шесть default outputs и stats
байт-в-байт. После замечания о неполной provenance исходного JSON выполнен ещё
один запуск в `upstream-results-verified.json` с явными `{}`. В
`upstream-reproduction-metadata.json` записаны SHA входа, обоих результатов,
comparison, адаптера и всех upstream `.ts`, commit, Node version и команда.
Исходный `upstream-results.json` сохранён без перезаписи. Проверка ограничена
этими fixtures: upstream test suite и реальные пользовательские PNG не запускались.

Пример повторного запуска с новым именем результата:
`node --experimental-transform-types .scratch/run-upstream-reference.mjs
.scratch/clipbrook-core-reference .scratch/upstream-inputs.json
.scratch/upstream-results-new.json`.

## Первоначальный аудит

Дата: 2026-09-09. Статус: исследование, не реализация.

## Зачем этот документ

Пользователь заметил на финальном PNG яркие красные, жёлтые и зелёные пиксели
на границе после удаления синего фона, а также недостаточно ровный контур.
Цель исследования — понять, какие механизмы дают аккуратный край у
`clipbrook-core`, где текущий алгоритм Vibix может создавать цветовые перекосы,
и как проверить улучшения, не уничтожив волосы, веточки, отверстия и мелкие
непрозрачные детали.

Это не утверждение, что upstream гарантирует лучшее качество на всех
изображениях. Исходный PNG и готовый PNG из примера не были предоставлены,
поэтому причина конкретного визуального дефекта пока не доказана.

## Подтверждённый дефект текущего автоматического пути

`remove_chroma_key_automatic` выбирает два разных математических алгоритма:
`precise`, если вторые каналы измеренного ключа не выше 36, и `staged` иначе.
На известной синтетике переход 36 → 37 меняет результат при одинаковом
исходном краевом пикселе.

| Измеренный синий фон | Итоговый край Vibix | Итоговый центр Vibix | Известная истина |
| --- | --- | --- | --- |
| `(2, 36, 250)` | `(212, 114, 125, 71)` | `(166, 97, 153, 184)` | край `(120, 80, 180, ~128)`, центр `(120, 80, 180, 255)` |
| `(2, 37, 250)` | `(123, 78, 152, 124)` | `(120, 80, 180, 255)` | та же |

Сцена: непрозрачный фиолетовый квадрат `(120, 80, 180)` на синем фоне;
верхний ряд имеет истинную alpha 0.5. Для `precise` расчёт alpha по доминированию
синего ошибочен на фиолетовом foreground. Затем эта alpha применяется при
восстановлении RGB и создаёт красноватый оттенок. Это доказанный дефект
синтетики, но не доказательство причины именно пользовательского скриншота.

Связанные места: `chroma_key.py:986` (маршрутизация), `:172` (fallback alpha),
`:298` (восстановление RGB).

## Что в upstream особенно полезно исследовать

| Принцип | Что делает upstream | Состояние у Vibix | Почему это важно |
| --- | --- | --- | --- |
| Единый pipeline | classify → band solve → pockets → despill → finish | два резко переключаемых пути + общие postprocess | Предсказуемость важнее случайного выбора иной математики по одному порогу. |
| Core / band | отделяет уверенный объект, уверенный фон и область сомнения | staged имеет аналог, precise — другую модель | Краевые пиксели не должны сразу считаться полностью объектом или фоном. |
| Многоуровневый reference | берёт цвет глубины 12/6/3/2 px, доступный для каждой точки | reference используется после основного solve | Тонкая ветка не имеет глубины 12 px; ей нужен ближайший надёжный внутренний цвет. |

| Finalization | alpha floor и очистка островков | малое alpha blur только в staged | Финальная кромка требует геометрического теста ширины, а не «на глаз». |

## Принципы, которые нельзя переносить без испытаний

- Удаление всех островков меньше 800 px. Это способно удалить волоски,
  тычинки, мелкие листья и отдельные веточки.
- Фиксированные радиусы 12/6/3/2 px. Они должны проверяться на разных
  разрешениях и толщине деталей.
- `alphaFloor = 0.08`. Он вырезает слабую coverage и может сделать край грубее.
- Pocket topology как доказательство фона. Замкнутая область бывает и частью
  объекта.
- Принудительное ограничение настоящих синих/фиолетовых деталей.
- Усреднение RGB reference как обычное «сглаживание».
- Метрика остаточного key-color как единственный критерий качества: синий край
  можно превратить в жёлтый, формально снизив эту метрику.

## Отдельные риски текущего Vibix

1. `precise/staged` имеют разный результат на границе измеренного порога 36.
2. `precise` может превратить собственный цвет объекта в дополнение ключа.
3. Нынешнее финальное восстановление исходного RGB защищает реальные
   key-подобные непрозрачные детали, но также отменяет некоторые успешные
   исправления spill. Его нельзя просто удалить: нужна политика уверенности.
4. Последующий `MinFilter(3)` в `main.py` может срезать тонкие детали уже после
   успешного chroma-key. Качество нужно измерять до и после всех postprocess и
   upscale, а не только на выходе функции keyer.
5. Текущие тесты проходят, но не проверяют скачок около 36, p95/max цветовой
   ошибки, ширину перехода alpha и локальные цветные выбросы.

## Почему появляются красные, жёлтые и зелёные точки

Если код пытается убрать синий, он может уменьшить blue channel сильнее, чем
red/green. Кремовый пиксель тогда становится желтоватым, розовый — красным,
оливковый — более зелёным. Если alpha ошибочно посчитана маленькой, обратное
восстановление RGB дополнительно усиливает неключевые каналы. Это не всегда
«остаток синего фона»: иногда алгоритм создаёт новый ложный оттенок.

На контролируемой фиолетовой синтетике это подтверждено без JPEG, генератора
или искусственных артефактов. Для `g=36` автоматический путь выдаёт край
`(212,114,125,71)` вместо `(120,80,180,~128)`. При `g=37` тот же пиксель
получает намного более правильный `(123,78,152,124)`. Это объясняет, почему
простая метрика «осталось ли мало синего» недостаточна: можно убрать blue,
но испортить картинку красно-жёлтой каймой.

## Конфликт opaque RGB repair и защиты настоящего цвета

В Vibix финальная `_preserve_fully_opaque_source_rgb` отменяет некоторые
исправления RGB в непрозрачной области. На существующей fixture:

| Стадия | Центральный пиксель |
| --- | --- |
| Источник | `(160,148,159)` |
| Known truth spill-free | `(205,190,132,255)` |
| После neutralize opaque spill | `(205,190,132,255)` |
| После final restore | `(160,148,159,255)` |

Это не ошибка, которую можно «просто удалить». Текущая регрессия намеренно
сохраняет исходный цвет, поскольку automation не может доказать, что это spill,
а не реальная голубая деталь объекта. Новый профиль обязан заменить эту
защитную функцию более точной политикой confidence, а не убрать её.

## Что реально проверяют текущие тесты

- 28 текущих chroma tests прошли: 16 `test_chroma_key` и 12
  `test_chroma_fine_detail`.
- Они не ловят синтетический порог 36, широкий непрозрачный фиолетовый
  foreground или локальные p95/max RGB выбросы.
- Один существующий edge-detail test принимает `alpha < 255` для исходно
  непрозрачной key-coloured детали. Он проверяет отсутствие полного отказа,
  но не доказывает сохранение opacity.
- `chroma_benchmark.py` считает средние alpha/RGB, IoU, leakage и opaque loss.
  Он не считает p95/max, толщину AA, topology или число локальных цветных
  выбросов.
- Fine-detail tests композят на чёрной, белой и маджентовой подложках, но
  усреднение по большому полотну может скрыть небольшой, но заметный дефект.
- Upstream golden assets отсутствуют в скачанном репозитории; golden suite
  пропускается, если нет внешнего `testdata/goldens`. Его golden parity —
  сравнение port с референсным Python keyer, не independent known-truth.
- Upstream test suite не запускался: в исследовательской копии нет готовых
  Node dependencies, а установка зависимостей не входила в это read-only
  исследование. Это не подменяется заявлениями README о parity.
- Отдельная stress-синтетика staged с разноцветными соседними foreground
  полосами и двумя AA-рядами дала mean max-channel edge error 63.8/255,
  p95 около 114.8 и max 180; edge alpha MAE 0.244. Это не оценка типичного
  качества, но повод не считать локально усреднённый reference доказанно
  безопасным на цветных стыках.

## Полный план экспериментов и измерений

### 1. Независимый known-truth набор

Создать версии с точной alpha и RGB: наклонные линии, дуги, завитки, волосы,
ветви толщиной 0.5/1/2/3/5 px, развилки, отдельные мелкие элементы, отверстия
1/2/4/8/16 px, плотные соседние детали разных цветов. Палитра: near-black,
white, warm neutral, red, yellow, olive, purple, light blue, цвета около key
и цвета, совпадающие с key. Последняя группа проверяет честную
неопределённость, а не невозможное обещание.

### 2. Controlled backgrounds

Каждая truth-сцена композится на blue/green/magenta, чистом primary и
реалистичном off-key фоне. Отдельно: secondary-channel sweep 30…42, spill,
пространственный gradient, pockets, JPEG quality/subsampling и шум. Сначала
чистый PNG, чтобы отделить ошибку модели от деградации исходника.

### 3. Диагностика каждого этапа

Отдельно запускать precise, staged, automatic и новый единый профиль. Хранить
только в локальном trace: measured key, выбранную ветку, core/band masks,
reference RGB/coverage/depth, determinant/stable, coefficients до/после
clamp, reconstruction residual, RGB до clamp и masks despill/projection/restore.
Это необходимо, чтобы объяснять Review, не отправляя пользовательские данные
в сеть.

### 4. Метрики по meaningful ROI

- Alpha: MAE/p95/max для opaque interior, AA, thin detail, holes/background;
  потеря площади и opaque pixel count.
- Контур: displacement p95/max, ширина alpha 0.05…0.95 по нормали, доля
  partial pixels дальше 2px от true edge.
- RGB: mean/p95/max channel error и max-channel error отдельно для opaque,
  AA и low-alpha edge.
- Цвет: signed обе стороны bias, absolute chroma error p95/max, число новых
  красных/жёлтых/оливковых выбросов relative to truth.
- Детали: component recall, endpoints/branches continuity, потерянные holes и
  ошибочно объединённые части.
- Предсказуемость: небольшое изменение input в sweep не даёт большого
  непомеченного скачка color/geometry.

### 5. Проверка финального pipeline

Сравнивать результат сразу после chroma и после всех стадий `main.py`, включая
upscale/resize и cleanup с MinFilter repeat 0/1/2/3. Результат на экране не
заменяет проверку экспортированного PNG. Для разрешённого внешнего upscale
нужен подтверждённый alpha-contract; иначе он разрешён лишь до keying либо
результат переходит в Review.

### 6. Ablation, а не массовый перенос

Сначала убрать или заменить небезопасную selector logic и сделать precise
validity tests. Затем по одному испытать: pre-solve interior reference/rim
demotion, brightness gate, guarded solve/clamp, no-reference policy и
confidence-limited RGB repair. Pockets/final alpha — после этого. Так будет
понятно, какой этап реально улучшил край и какой навредил веточкам.

## Как доказать улучшение

Нужен самостоятельный набор known-truth RGBA fixtures, а не только совпадение
с чужим алгоритмом:

1. Непрозрачные тела, наклонные линии, волосы и ветки толщиной 0.5/1/2/3/5 px,
   развилки, отверстия, отдельно стоящие мелкие элементы и соседние детали
   разных цветов.
2. Один и тот же объект на синих, зелёных и маджентовых ключах, с чистым PNG,
   off-key фоном, известным spill, шумом и JPEG отдельно.
3. Отдельные прогоны `precise`, `staged`, нового единого пути и каждого этапа
   postprocess.
4. Метрики в значимых областях: alpha MAE/p95/max, RGB MAE/p95/max, число
   новых красных/жёлтых/оливковых выбросов, смещение контура, ширина alpha
   0.05…0.95, component/holes recall и сохранение развилок.
5. Композиции результата на чёрном, белом и маджентовом фоне. Метрики считать
   на краевой ROI, не на всём пустом холсте.
6. Приёмка только на финальном PNG после resize/upscale/cleanup: для
   непрозрачного профиля нет подтверждённой полупрозрачной зоны шире 2 px,
   кроме истинной subpixel coverage тонкой детали.

## Первый проверенный increment после аудита

Пользователь поручил реализацию. Введён отдельный `opaque_clipart` профиль:
предположение о непрозрачности задаётся вызывающим кодом, а не выдаётся за
доказанный результат анализа RGB. Local Chroma Key приложения использует этот
профиль. Сигнатура общего Python API по умолчанию сохраняет `legacy`.

Новый профиль использует локальную опору цвета для подходящих замкнутых
областей до восстановления RGB. Объём суммарных ROI ограничен четырьмя
площадями изображения. Existing source alpha остаётся верхней границей.
Это ограниченное исправление найденного дефекта; полная замена staged,
подтверждение ширины сглаживания, provenance и Review ещё не реализованы.

`scripts/benchmark_chroma_selector.py` воспроизводит исходный квадрат на 39
комбинациях цвета ключа и его вторичного канала. Входы/истина/engine снабжены
hash; новая offline-метрика не используется как QA реальных изображений без
known truth.

| Случай | До исправления RGBA | Профиль opaque_clipart RGBA |
| --- | --- | --- |
| Blue, secondary36, центр | `(166,97,153,184)` | `(120,80,180,255)` |
| Blue, secondary36, край | `(212,114,125,71)` | `(120,80,180,128)` |
| Blue, secondary37, край | `(123,78,152,124)` | `(120,79,180,127)` |

На всём этом sweep максимальная поканальная ошибка RGB края: 92 → 1 из255;
максимальная ошибка alpha в непрозрачном центре: 71 → 0 из255. Эти значения
относятся только к указанному синтетическому набору. Скрипт запускается с
`--subject-profile opaque_clipart --output <новый-путь.json>`; существующий
файл отчёта не перезаписывается. До/после сохранены локально в `.scratch`.

## Ограничения вывода

Upstream golden assets отсутствуют в скачанной копии; его тесты могут
сравнивать port с собственным эталоном и не доказывают абсолютное качество.
Финальное решение о новой архитектуре принимается после реализации
instrumented benchmark и проверки на пользовательских парах «до/после».
