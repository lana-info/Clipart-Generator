# Windows 3.0.5 Stabilization And Parallel Generation Design

## Goal

Prepare a stable Windows 3.0.5 source candidate before starting another build.
The candidate must preserve the accepted navigation and completion behavior,
offer only Topaz 2x and 4x, and run independent KIE generation tasks in
parallel while showing every active item accurately in Results.

## Scope

Included:

- verify and retain the accepted clean-start, same-mode restart, completion
  summary, result preview, CSV import, and no-processing navigation behavior;
- retain Topaz upscale choices at 2x and 4x only, including migration of stale
  unsupported values;
- run up to three generation-only KIE tasks concurrently;
- start KIE generation tasks through the existing bounded launch limiter;
- associate start, stage, output, error, cancellation, and completion events
  with the exact prompt row;
- show more than one Results row as running when more than one task is active;
- preserve sequential generation as a fallback when concurrency is set to one;
- verify all source changes before any Windows build is requested.

Excluded:

- fal.ai integration;
- changes to Recraft availability or fallback behavior;
- parallel Topaz, PhotoRoom, local processing, or complete mixed pipelines;
- changing the release version, publishing a server revision, or starting a
  Windows/macOS build as part of implementation.

## User-Visible Behavior

Starting Clipart or Pinterest from mode selection always opens the first step
of a clean workflow. Starting again from Results clears only temporary queue
and result state, keeps safe settings and folders, and opens the first step of
the same mode. Completion shows the compact summary and leaves the complete
Results page available after the dialog closes.

Topaz exposes only 2x and 4x. A stale 1x, 3x, or otherwise unsupported stored
value is normalized to the existing safe default instead of returning to the
interface.

For generation-only runs, up to three prompt rows may display `выполняется` at
the same time. The Results header reports active, completed, failed, and waiting
counts from row states. Each result, error, and diagnostic event remains bound
to its originating prompt even when tasks finish out of order.

## Event And Queue Design

The worker emits structured progress events for item lifecycle changes. Every
event that can mutate a Results row carries `item_index`, `total_items`,
`stage`, `status`, and a bounded user-safe message. Output publication also
carries the exact item index rather than depending on one shared
`current_index` cursor.

`RunQueueSession` updates the item named by an event. It may therefore hold
multiple `RUNNING` items concurrently. The legacy text parser remains only as
a compatibility fallback for sequential workers and must not be used to route
parallel output or errors.

Generation tasks keep per-item diagnostic context and isolated intermediate
and final paths. The existing launch limiter and bounded HTTP 429 backoff stay
in force. One failed generation marks only that item failed and does not cancel
unrelated work. Stop requests prevent new submissions and safely settle tasks
already in flight.

## Safety And Cost Controls

- The release default remains three concurrent generation tasks.
- No provider availability probe creates a paid task.
- POST retries remain limited to cases known not to have created a paid task,
  such as a rejected HTTP 429 response.
- Output paths remain isolated by prompt index and run stamp.
- Prompts, API keys, raw provider responses, and full personal paths do not
  enter user-facing diagnostics.
- Recraft failure never silently falls back to another paid model.

## Verification

Tests are written before implementation and must demonstrate:

- three independent generation calls overlap and preserve prompt indexes;
- three rows can be `RUNNING` simultaneously;
- out-of-order success and failure update the correct rows;
- a successful output never terminates or overwrites another active item;
- cancellation prevents new submissions and settles active/pending rows;
- HTTP 429 is bounded and does not lose the remaining queue;
- sequential mode still works;
- Topaz exposes only 2x and 4x and migrates unsupported saved values;
- clean start, same-mode restart, completion summary, preview dismissal, CSV,
  and no-processing regressions continue to pass.

The focused queue and navigation suites run first, followed by the complete
offscreen test suite, compilation, sensitive-artifact scan, and
`git diff --check`. A Windows build is a separate, explicitly initiated step
after source verification and integration approval.
