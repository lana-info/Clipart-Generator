# Windows 3.0.5 Stabilization And Provider-Aware Parallel Work Design

## Goal

Prepare a stable Windows 3.0.5 source candidate before starting another build.
The candidate must preserve the accepted navigation and completion behavior,
offer only Topaz 2x and 4x, and run independent KIE and PhotoRoom tasks in
parallel while showing every active item accurately in Results.

## Scope

Included:

- verify and retain the accepted clean-start, same-mode restart, completion
  summary, result preview, CSV import, and no-processing navigation behavior;
- retain Topaz upscale choices at 2x and 4x only, including migration of stale
  unsupported values;
- expose separate KIE and PhotoRoom concurrency settings with choices 1, 2,
  and 3 and a release default of 3 active tasks for each provider;
- enforce a fixed release-wide safety cap of 6 simultaneous network tasks;
- apply the shared limit to generation, Topaz upscale, KIE background removal,
  and every other already supported KIE operation;
- apply the PhotoRoom limit to all already supported PhotoRoom processing;
- start KIE tasks through the existing bounded launch limiter;
- preserve the selected stage order within each image while allowing KIE
  stages from different images to overlap;
- associate start, stage, output, error, cancellation, and completion events
  with the exact prompt row;
- show more than one Results row as running when more than one task is active;
- preserve sequential KIE work as a fallback when concurrency is set to one;
- verify all source changes before any Windows build is requested.

Excluded:

- fal.ai integration;
- changes to Recraft availability or fallback behavior;
- parallel local processing;
- changes to the request/response contract of any existing Recraft operation;
- changing the release version, publishing a server revision, or starting a
  macOS build. A Windows-only 3.0.5 build follows only after the source is
  verified and integrated.

## User-Visible Behavior

Starting Clipart or Pinterest from mode selection always opens the first step
of a clean workflow. Starting again from Results clears only temporary queue
and result state, keeps safe settings and folders, and opens the first step of
the same mode. Completion shows the compact summary and leaves the complete
Results page available after the dialog closes.

Topaz exposes only 2x and 4x. A stale 1x, 3x, or otherwise unsupported stored
value is normalized to the existing safe default instead of returning to the
interface.

For generation and processing runs, several rows may display `выполняется` at
the same time whenever independent KIE operations are active. The Results
header reports active, completed, failed, and waiting counts from row states.
Each result, error, and diagnostic event remains bound to its originating
prompt or input file even when tasks finish out of order.

The settings show separate selectors for KIE and PhotoRoom. Each selector has
only 1, 2, and 3 because this release intentionally supports no higher value.
Choosing 1 preserves the sequential fallback for that provider. KIE may run up
to three tasks and PhotoRoom may independently run up to three tasks, while the
application never runs more than six network tasks in total. Local operations
continue to run one at a time in this release.

## Event And Queue Design

The worker emits structured progress events for item lifecycle changes. Every
event that can mutate a Results row carries `item_index`, `total_items`,
`stage`, `status`, and a bounded user-safe message. Output publication also
carries the exact item index rather than depending on one shared
`current_index` cursor.

`RunQueueSession` updates the item named by an event. It may therefore hold
multiple `RUNNING` items concurrently. The legacy text parser remains only as
a compatibility fallback for sequential workers and must not be used to route
parallel output or errors.

Every image job keeps per-item diagnostic context and isolated intermediate and
final paths. Its stages execute in the selected order. Before an existing KIE
adapter submits a paid operation, it acquires one slot from the KIE provider
semaphore; the slot remains occupied until that provider task reaches a
terminal state. PhotoRoom operations acquire a separate PhotoRoom semaphore.
Both provider semaphores sit behind one six-worker network executor, so three
KIE and three PhotoRoom operations may overlap but a seventh network operation
cannot start. Local adapters keep their existing single-operation lock and do
not consume provider slots.

The existing KIE launch limiter and bounded HTTP 429 backoff stay in force.
PhotoRoom additionally receives a provider launch guard that permits an
initial burst of up to three calls and then limits sustained starts to the
documented default budget of 60 images per minute. A PhotoRoom HTTP 429 remains
bounded and visible in diagnostics. One failed item marks only that item failed
and does not cancel unrelated work. Stop requests prevent new submissions and
safely settle tasks already in flight. Recraft keeps its current request
schema, availability behavior, and no-silent-fallback rule; only scheduling
around the existing adapter changes.

## Safety And Cost Controls

- The release default is three concurrent KIE tasks and three concurrent
  PhotoRoom tasks; each selector exposes only 1, 2, and 3.
- The KIE limit is shared by KIE generation and processing, so selecting 3 can
  never create 3 generation plus 3 upscale plus 3 removal tasks at once.
- The fixed overall network cap is six, preventing provider limits from
  multiplying beyond the reviewed release envelope.
- No provider availability probe creates a paid task.
- POST retries remain limited to cases known not to have created a paid task,
  such as a rejected HTTP 429 response.
- Output paths remain isolated by prompt index and run stamp.
- Prompts, API keys, raw provider responses, and full personal paths do not
  enter user-facing diagnostics.
- Recraft failure never silently falls back to another paid model.

## Verification

Tests are written before implementation and must demonstrate:

- three independent KIE calls overlap and preserve item indexes;
- three independent PhotoRoom calls overlap and preserve item indexes;
- a mixed run can reach three active KIE plus three active PhotoRoom tasks but
  never exceeds six active network tasks;
- generation-only, processing-only, and generate-then-process runs all obey the
  same KIE concurrency limit;
- Topaz and KIE background-removal tasks can overlap across different items,
  while each individual item preserves its stage order;
- setting either provider to 1 preserves sequential behavior for that provider;
- local operations remain sequential;
- PhotoRoom sustained starts respect the 60-images-per-minute launch guard and
  bounded HTTP 429 handling;
- existing Recraft payloads and failure behavior are unchanged;
- three rows can be `RUNNING` simultaneously;
- out-of-order success and failure update the correct rows;
- a successful output never terminates or overwrites another active item;
- cancellation prevents new submissions and settles active/pending rows;
- HTTP 429 is bounded and does not lose the remaining queue;
- obsolete saved values above 3 migrate safely to 3 for both providers;
- Topaz exposes only 2x and 4x and migrates unsupported saved values;
- clean start, same-mode restart, completion summary, preview dismissal, CSV,
  and no-processing regressions continue to pass.

The focused queue and navigation suites run first, followed by the complete
offscreen test suite, compilation, sensitive-artifact scan, and
`git diff --check`. After successful source verification, the feature branch
is integrated into `develop/3.0`, verified again, pushed, and used for the
explicitly approved Windows-only 3.0.5 installer build. The build must retain
the approved application and Inno Setup artwork. Server publication remains a
separate owner decision after target-Windows acceptance.
