# Общий хост модулей: новый модуль без новой сборки Studio — варианты (2026-10-23)

Цель владельца: Studio обновляется редко, новый модуль просто появляется у клиентов.

## Что мешает сейчас (проверено по коду develop/3.2)
- Карточка модуля зашита в ядро: `studio_catalog_ui.py` (`CatalogEntry("patterns", …)`, обложка в assets).
- Список известных модулей зашит: `studio_module_delivery.py` (`EXISTING_WORKFLOW_IDS | {…, "patterns"}`).
- Открытие — отдельный код на каждый модуль: `v3_mode_selection.py` (`if module_id == "patterns": self._open_patterns()`),
  а хост страницы (`studio_patterns_host.py`) лежит в ядре.
- Общая часть уже есть: `studio_module_runtime` умеет `load_active`, `invoke_command`, `create_page` — Patterns
  открывает страницу через неё.

## Варианты
1. **Общий хост (рекомендую).** Один раз в ядре: каталог берёт карточки (название, описание, обложку) из подписанного
   пакета/сервера; одна функция `open_module(module_id)` — проверка права, загрузка, `create_page(module_id, "main",
   host)`; универсальный `ModulePageHost` (папка данных модуля, сигналы «Главная / API / Диагностика», журнал,
   проверка лицензии при открытии). Модуль приносит свою страницу и свою логику в пакете. После одной сборки Studio
   новые модули ставятся без пересборки.
2. **Оставить как есть.** Каждый новый модуль — правка ядра + новая сборка Studio. Просто, но против цели.
3. **Промежуточно.** Только каталог с сервера, открытие по-прежнему отдельным кодом — модуль всё равно требует сборки.

## Риски варианта 1
- Модуль получает больше возможностей в процессе Studio: только подписанные пакеты (как сейчас, ключ vibix-publisher-v1),
  проверка совместимости версий ядра.
- Перевод существующих модулей (Patterns, Конструктор промптов) на общий хост — отдельными шагами с тестами.
- Нужна одна новая сборка Studio; карточки каталога — макет (визуальный шлюз) только если меняется вид.
