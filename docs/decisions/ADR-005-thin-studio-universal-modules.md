# ADR-005: Тонкая Studio, универсальные модули, порядок модулей

Статус: ПРЕДЛОЖЕНО 2026-10-26 (план, код не менялся; решение за владельцем).
Связано: ADR-004, STATE.md «Как устроены модули и обновления», TASKS.md «Общий хост модулей».

## Цели владельца
1. Studio обновляется редко; новые модули и их правки приходят отдельно.
2. Владелец сама меняет порядок модулей на главной.
3. Модуль публикуется на сервере ОДНИМ файлом для Windows и macOS (сейчас два).

## Что есть сейчас (проверено по коду 2026-10-26)
- Подписанный пакет модуля (zip) уже содержит в `manifest.json` СПИСОК `platforms`
  (studio_module_packaging.py); клиент (`ModuleStore`) принимает пакет, если его платформа есть в списке.
  Значит формат уже допускает один пакет на обе системы.
- Сервер лицензий хранит релиз как строку с ОДНОЙ `platform` (licensing.py, postgres_store.py `releases`),
  Studio ищет релизы по своей платформе. Отсюда два файла на модуль.
- Обновление установленного модуля идёт без новой Studio. ПЕРВОЕ появление модуля требует новой Studio:
  карточка каталога (`BUILTIN_CATALOG` в studio_catalog_ui.py, плитки в v3_mode_selection.py),
  открытие страницы и Core-хост задач/доступа написаны внутри Studio.
- Порядок карточек задан порядком кортежа `BUILTIN_CATALOG`; пользовательских настроек порядка нет.
  Локальные настройки уже лежат в `preferences.json` рядом с черновиком.

## Решения
### A. Универсальный хост модулей (тонкая Studio)
- Каталог: сервер отдаёт записи (module_id, название, описание, картинка, минимальная Studio, `module_api`).
  Карточка строится из каталога/манифеста, а не из кода Studio. Встроенный список остаётся как запасной.
- Манифест модуля объявляет точку входа страницы: `create_page(host_api)`; Studio имеет ОДНУ универсальную
  точку открытия страницы модуля.
- `host_api` версионируется (`module_api`): задачи/очередь, доступ по лицензии, проекты и файлы, настройки,
  диагностика. Studio меняется только при смене host_api; модуль объявляет нужную версию, несовместимый
  не включается, остальные работают.
- Переносим Patterns (пилот), затем Prompt Composer. Четыре основных модуля (generation, auto-clipart,
  processing, pinterest) пока остаются встроенными: связаны с ядром слишком глубоко.
- Принцип ADR-004 сохраняется (доверенные подписанные модули, оплата и сохранение проектов — за Core).

### B. Порядок модулей
- Сохранение: ключ `module_order` (список module_id) в локальном `preferences.json`; не на сервере.
- Правила: неизвестные id игнорируются, новые модули встают в конец по порядку каталога, «Сбросить порядок».
- Интерфейс: режим «Изменить порядок» (иконка у заголовка «Модули»), на плитке стрелки влево/вправо
  (доступно с клавиатуры), перетаскивание — опционально. Без пояснительных подписей. НУЖЕН макет и одобрение
  владельца (визуальный барьер проекта).

### C. Один файл модуля для обеих систем
- Шаг 0: сверить, что файлы Windows- и macOS-пакетов одной версии побайтно совпадают (модули — Python без
  нативных частей). Если есть различия — вынести в раздельные ресурсы, пакет остаётся один.
- Пакет: `platforms` = [windows-x64, macos-arm64, macos-x64]; сборка одной командой; проверка установки на
  каждой заявленной платформе уже есть в `prepare_official_workflow_release`.
- Сервер: релиз модуля с платформой `any` (или несколькими), выдача по запросу любой платформы; миграция БД;
  старые клиенты (3.2.43 и ранее) запрашивают свою платформу — сервер обязан вернуть универсальный пакет,
  а проверка `platforms` у них пройдёт. Старые двухфайловые релизы остаются, новые — одним файлом.
- Скрипты публикации (`upload-set`, `promote`, publish-*.sh) и runbook — на один файл. Публикацию на
  сервер делает агент; пароль/TOTP — владелец.

## Порядок работ, сложность, срок
Срок — рабочие дни агента вместе с проверкой и приёмкой владельцем; без учёта ожидания ответов.

| № | Задача | Сложность | Срок | Зависимости |
|---|--------|-----------|------|-------------|
| B | Порядок модулей (макет, настройка, режим правки, тесты) | Низкая–средняя | 1–2 дня | макет владельцу |
| C0 | Сверка пакетов Windows/macOS | Низкая | 0,5 дня | — |
| C1 | Универсальный пакет + сервер (миграция, выдача, совместимость со старыми клиентами) + скрипты | Средняя | 2–3 дня | C0; публикация владельцем |
| A1 | Спецификация host_api v2 и схемы каталога (ADR) | Средняя | 2–3 дня | решение владельца |
| A2 | Динамические карточки каталога из сервера/манифеста | Средняя | 2–3 дня | A1 |
| A3 | Универсальное открытие страницы модуля | Средняя | 2 дня | A1 |
| A4 | Перенос Patterns на хост (пилот) | Средняя–высокая | 3–4 дня | A2, A3 |
| A5 | Перенос Prompt Composer | Средняя | 3 дня | A4 |
| A6 | Совместимость и откат: старая Studio + новые модули, новая Studio + старые модули; релиз Studio один раз | Высокая | 2–3 дня | A4, A5 |
Итого: B+C ≈ 4–6 дней; A ≈ 14–18 дней. Рекомендуемый порядок: B и C0→C1 (быстрая польза, небольшой
риск), затем A (делать до появления 3–4 новых модулей). Только C затрагивает сервер лицензий (боевой).

## Риски
- Сервер лицензий боевой: миграция и выдача «any» только с тестами и совместимостью со старыми клиентами.
- Пока host_api не стабилен, каждое его изменение всё равно требует новой Studio; поэтому A1 делать тщательно.
- Перенос модулей без регрессий в доступе по лицензии (проверка прав на каждый module_id).
