# Макет: перетаскивание PNG из проводника в три места (владелец 2026-10-30)

Статус: **макет; правило замены по имени `_NN_ready` и диалог «Куда поставить» заменены 2026-11-01: бросок добавляет НОВУЮ позицию, замена — только Shift + бросок на картинку (см. `docs/ERRORS.md`, #drop-adds-items-20261101).** До правок — обязательный визуальный допуск
(AGENTS.md, «Mandatory visual approval gate»). Ветка задачи начинается от свежей
`origin/develop/3.2`. Ограничение приёмки: 1120×780 при 100 % масштабе.

## Файлы

| Файл | Экран |
|---|---|
| `nabory.html` | Страница наборов (шаг «Экспорт», таблица наборов, ✓/✎/⇅) |
| `rezultaty.html` | Страница «Результаты» («Выполнение и результаты», модуль Авто-клипарт) |
| `proverka-png.html` | Страница «Проверка PNG» (сетка миниатюр + карточка картинки) |
| `*-*.png` | Снимки всех состояний (по 4–5 на экран), сняты Chrome headless 1120×780 |

Состояния переключаются адресом: `nabory.html?state=hover` (`normal`, `hover`,
`rejected`, `success`; у «Результатов» ещё `confirm`; у «Проверки PNG» — `picker`).

## Что меняется и что нет (пересказ по-простому)

**Меняется одно:** на трёх экранах можно взять PNG-файл в проводнике Windows и
бросить его в окно — файл станет готовой картинкой одной из позиций запуска, без
новой генерации и платных запросов. Это то же самое, что кнопка «Вернуть готовые
файлы», но файл берётся прямо из проводника (хоть из «Загрузок»), а не только из
папки результата.

**Не меняется:** состав таблицы и сетки, все нынешние кнопки и значки (✓/✎/⇅,
метки, фильтры, «Редактировать прозрачность»), правило SET-0 («в наборы попадают
только картинки с „Ок“»), «История версий», корзина. Во время работы запуска
перетаскивание выключено — как и «Вернуть готовые файлы» сейчас.

Действие, которое должно поддерживаться (слова владельца 2026-10-30): перетащить
файл из проводника (1) в набор — на страницу наборов, (2) на страницу
«Результаты», (3) на страницу проверки PNG.

## Единая семантика (рекомендация, минимум нового кода)

Один и тот же приём файл работает на всех трёх экранах; различается только
подсветка под курсором.

**Куда попадает файл.** Файл **копируется** в папку результата запуска и
подключается к одной из **существующих позиций** — ровно тем же путём, каким
«Вернуть готовые файлы» (`studio_auto_clipart_flow.recover_results`):
`keep_version` (прежняя картинка позиции → «История версий»), затем
`item.output_path = <новый файл>`, `review_mark, review_checked = "ok", False`
(метка «Не проверено», статус «Готово»), `session.changed.emit()` + сохранение
прогона + обновление страницы. Имя копии — по шаблону позиции:
`<тема файла>_<NN>_ready.png` (NN = выбранная позиция; коллизия имени — суффикс
`_2`, как `output_naming.reserve_processed`).

**Как выбирается позиция (одно правило на все экраны):**

1. **Бросил НА строку/миниатюру/ячейку** — файл встанет на позицию этой строки
   (приоритет у строки, не у имени файла). Если на позиции уже есть картинка —
   вопрос в стиле «Вернуть готовые файлы»: «Прежняя станет версией», «Да /
   Нет». Свободная позиция (картинки нет после прерванного запуска) — ставим
   без вопроса.
2. **Бросил мимо (пустое место списка/сетки/таблицы/окна)** — позицию
   подсказывает **имя файла**: в имени есть `_NN_ready` и NN в диапазоне позиций
   — берём NN (для файлов, названных самим приложением). Иначе — небольшой
   диалог **«Куда поставить …?»**: миниатюры всех позиций с номерами; если на
   позиции уже есть картинка, она видна; выбор — «Поставить», отмена.
3. **Новых позиций не создаём.** Позиции запуска = промптам (шаги 4–6 их
   задали); без промпта не работают «Переделать выбранные», версии и т.п.
   Это стоит признать владельцу явно (см. открытые решения ниже).

**Наборы — дроп на ячейку колонки набора** (страница наборов): то же подключение
к позиции строки + **намерение набора запоминается** — новый файл сразу
получает `included = True` в этом наборе (membership-запись). Но строка появится
в таблице и галочка станет видимой **только после «Ок»** (SET-0) — на макете
успеха это объясняет зелёная плашка и «фантомная» строка. До «Ок» картинка
видна в «Проверке PNG» со статусом «Не проверено». Дроп на колонку «PNG» или на
пустое место = просто подключить, галочки не трогать.

**Метки.** Всегда «Не проверено» до её «Ок» (так у возвращённых:
`review_mark="ok", review_checked=False`). Прежняя подтверждённая картинка
позиции теряет «Ок» автоматически — она же стала версией.

**Чужие имена файлов.** Работают: копия называется `<stem файла>_<NN>_ready.png`
(stem очищается от недопустимых символов и укорачивается, кириллица
сохраняется). Только цифра NN никогда не берётся из «мимо»-дропа чужого имени —
спрашиваем выбор позиции.

**Откуда принимаем (правила приёмки, по `_safe_png` + `MAX_PREVIEW_BYTES`):**

| Правило | Значение | Отказ (красная плашка внизу экрана, не блокирует работу) |
|---|---|---|
| Формат | `.png` + сигнатура файла `\x89PNG\r\n\x1a\n` (не только расширение) | «{имя} — это не PNG. Перетащите файл с расширением .png» / «{имя} — внутри не PNG (переименованный другой файл)» |
| Ссылки | симлинк/ярлык — не принимать | «{имя} недоступен (ярлык или ссылка)» |
| Размер | ≤ 64 МБ (как `MAX_PREVIEW_BYTES` в `v3_run_queue`) | «{имя} слишком большой (N МБ) — лимит 64 МБ» |
| Количество | ≤ 8 файлов за один дроп | «За раз можно 8 файлов — лишние (k) не приняты» |
| Папки | не принимать, файлы внутри не извлекать | «Папки не принимаются — перетащите PNG-файлы» |
| Дубликат | позиция уже показывает этот самый файл | «Эта картинка уже стоит на позиции NN» |
| Занятость | запуск идёт (`session.running` / `is_busy`) | дроп выключен, подсказка: «Во время работы запуска файлы не принимаются» |

Мультикопирование: файлы обрабатываются по порядку, счёт в итоговой плашке
(«Подключено: 3 · отклонено: 1 — …причина»).

## Открытые решения владельца (по 4 вопросам из TASKS.md)

1. **Куда попадает файл** → рекомендация: готовая картинка **существующей
   позиции** (расширение «Вернуть готовых файлов», максимум переиспользования);
   не строка-гость (ломает перегенерацию/версии — охранные правки в 3+ местах) и
   не референс генерации. Альтернатива «добавлять новой позицией в конце» —
   возможна, но дороже (см. «Альтернатива B» ниже) и меняет смысл «позиция = промпт».
2. **Метки** → «Не проверено» до «Ок», ровно как у возвращённых
   (`review_mark="ok", review_checked=False`). Подтверждено кодом, нового мнения
   не требует.
3. **Именование** → копия в папку результата под шаблон позиции
   `<stem>_<NN>_ready.png`; дроп на строку переобозначает файл под позицию
   («utka_03_ready.png», брошенный на строку 2, станет «utka_02_ready.png»).
   Нужно согласие: переименование копии — ок?
4. **Откуда принимать** → только PNG (расширение + сигнатура), не симлинки,
   ≤ 64 МБ, ≤ 8 файлов за раз, папки — отказ. Лимиты 64 МБ / 8 файлов —
   предложение, решает владелец.

Плюс одно новое решение, которого в TASKS.md не было: **прикреплять только к
существующим позициям** (рекомендация) или **разрешить новые позиции в конце
набора**. Альтернатива B («дроп на набор = новая позиция + галочка») оценена в
плане ниже и дороже; выбрав её, владелец получает изменение счётчиков и имен в
ZIP и требует охранных правок в «Переделать выбранные».

## План реализации (не код, порядок PR)

Точки в коде: `studio_set_export_ui.py` (quality_page — сетка `quality_list`;
summary_page — таблица `self.table`, `_rebuild_manual_table`),
`v3_run_queue.py` (`RunResultsPage`, `RunQueue`, `MAX_PREVIEW_BYTES`),
`studio_clipart_review_ui.py` (`install_results_page` — строка фильтров у списка),
`studio_auto_clipart_flow.py` (`_recoverable_outputs` / `recover_results` —
образец подключения), `studio_clipart_recovery.py` (`_safe_png` — сигнатура PNG),
`output_naming.py` (`_budgeted_filename`, суффиксы коллизий).

- **PR-1 (ядро, без изменения экранов):** общий модуль приёма `studio_clipart_drop`
  — валидация (сигнатура/симлинк/размер/количество/папки → понятные сообщения) +
  копирование в папку результата под шаблон позиции (`_budgeted_filename`) +
  выбор позиции (имя `_NN_ready` / строка под курсором / диалог). Тесты: валидация,
  коллизии имён, «файл = картинка позиции» (дубликат).
- **PR-2 («Проверка PNG»):** обработчики `dragEnterEvent/dragMoveEvent/dropEvent`
  + `setAcceptDrops` на `quality_list`; дроп на миниатюру = её позиция; после
  приёма — `mark_output`-like путь и автозапуск фонового PNG-чекера
  (`_start_png_check`). Риск: `_refresh_quality_page` пересобирает сетку — состояние
  дропа не хранить в элементах списка; сброс hover при пересборке (урок
  T-QUAL-5 и «прыжок сетки» 2026-10-30).
- **PR-3 (страница наборов):** сигнал `attach_requested` от `SetExportDialog` в
  flow (рядом с `regenerate_requested`), обработчик в flow — тот же
  `_attach_outputs` из PR-1; дроп на колонку набора проставляет `included=True`
  в membership до «Ок»; таблица перестраивается только через существующий
  `_refresh_export` (совместимость с SET-0). Риск: `_rebuild_manual_table`
  затирает выделение — не дропать состояние hover в чекбоксы.
- **PR-4 («Результаты»):** `setAcceptDrops` на `RunQueue` (или страница), дроп на
  строку = её позиция (индекс из `RunItem.index`), переиспользование вопроса
  замены из `recover_results`. Риск: строки скрываются фильтром — дроп «мимо»
  не должен попадать на скрытую строку под курсором.
- После каждого PR — снимки реального экрана в тех же состояниях и сравнение с
  макетом (правило визуального допуска). Сборки — только по команде владельца.

**Альтернатива B (если владелец выберет «новые позиции»)**: дополнительный PR-5 —
создание `RunItem` без промпта (с обычным `output_path`), охранные правки в
«Переделать выбранные»/«Пересоздать помеченные» (пропускать позиции без промпта
с объяснением), пересчёт имён ZIP. Оценка: заметно дороже, решать отдельно.

## Правила приёмки макета владельцем

1. На трёх экранах видно: обычное состояние, drag-hover с видимой приёмной
   подсветкой строки/ячейки/миниатюры, отказ с причиной, успех с «Не проверено».
2. Тексты плашек и вопроса замены читаются (воображаемый drop в статике —
   элементы ghost-подписи у курсора).
3. SET-0 соблюдён на макетах: перетащенная картинка попадает в набор только
   после «Ок» (фантомная строка и плашка это объясняют).
4. Решения по четырём открытым вопросам (и по «новым позициям») приняты — лишь
   после этого возможна реализация по плану выше.
